# Rack v2.1 plan (step 0): friends' accounts and Profile

Answers `docs/v2.1-brief.md` step 0, with the changes from 17 November 2026:

- **Profile replaces the settings cog** on the web and in the iOS app, in the same top-right spot:
  your photo, or a placeholder avatar (initials) until you set one. Tapping it opens Profile:
  your account (picture, name, username, member since, role) and a row into Settings (everything
  Settings has today).
- **Profile pictures**: change and remove your photo, on the web and in the iOS app.
- **Friends can see Sources** (the source health view), not just the owner.
- **Cloudflare Tunnel and public access are dropped from v2.1** (old step 6, including
  `docs/server-move.md`): later version. Until then friends can only reach the server over
  Tailscale (node sharing works on the free plan). Security is still built for the public internet.
- The iOS app stays yours (sideloaded), gets the username login, the Profile sheet with the photo,
  and the brief's inline titles. A fresh GitHub Actions build at the end, when you say.

## 1. Single-user assumptions today

| Where | Assumption | v2.1 |

## 2. Data model

New tables:
- `users`: id, `username` (unique, stored lowercase, 3-24 of `a-z 0-9 _ .`), `display_name`,
  `password_hash` (argon2), `role` (`owner` | `friend`), `created_at`, `disabled_at`,
  `session_epoch`, `avatar_version` (null = no photo), `last_active_at` (updated at most hourly).
- `invites`: id, `code_hash` (SHA-256 of a 128-bit random code; the code itself is shown once and
  never stored), `note`, `created_by`, `created_at`, `expires_at` (7 days), `used_at`, `used_by`,
  `revoked_at`.
- `user_state`: (user_id, key) → JSON, the per-user part of `app_state`.
- Alerts: friends get **Web Push only** (your choice). ntfy and Telegram stay owner-only and stay
  in `.env`; `push_subscriptions` gains `user_id`, so each user's pushes go to their own devices.

Shared and unchanged: `listings`, `listing_images` (photos and embeddings), `price_observations`,
`sold_listings`, `source_health`, global `app_state` keys.

Migration `0019_users` (tested on a `pg_dump` copy of the real database first):
1. Create `users`; insert the owner (username you choose, hash = current `RACK_PASSWORD_HASH`,
   epoch = current `app_state['auth'].epoch`).
2. Add `user_id` to every personal table, fill it with the owner's id, then make it NOT NULL and
   swap the primary/unique keys (`listing_scores`, `feedback`, `saved`, `seen` become
   (user_id, listing_id); `designers` unique (user_id, name); `hidden` (user_id, kind, value);
   `notifications.key` unique per user).
3. `profile.user_id` = owner; move `app_state['scoring'|'visit']` into `user_state`.
4. Move `uploads/*` to `uploads/<owner id>/` (a CLI step the migration prints, since files live
   outside Postgres; idempotent).
5. Check: row counts per table before = after; the owner's feed, Saved, hunts and wardrobe
   unchanged. Downgrade keeps working on the copy.

Cookies and tokens issued before the migration carry no user id, so they stop working: you log in
once more on the web and in the iOS app (the brief allows that).

## 3. Making it hard to forget the user

- `require_user` dependency returns the `User` (replaces `require_session`), and every router is
  mounted with it except an explicit allowlist (`/api/health`, login, token, logout, sign-up).
- One helper module `rack/scoped.py`: `owned(Model, user)` builds `select(Model).where(user_id=…)`,
  `get_owned(session, Model, id, user)` returns the row or 404 (never 403, so ids don't leak).
- Tests that fail the build if someone forgets: (a) every route except the allowlist answers 401
  without credentials; (b) every model with a `user_id` column is listed in the IDOR matrix;
  (c) the IDOR matrix: users A and B each get a full set of data, then A calls every endpoint with
  B's ids (read, change, delete, thumbnails, matches, undo) and must get 404 with B's data unchanged.

## 4. Login, sessions, invites

- Login: `POST /api/auth/login` and `/token` take `{username, password}`. Unknown users still pay
  for an argon2 verify against a dummy hash (same timing), and every failure says "Wrong username
  or password". Limits: 5 per IP and 5 per username per 15 min, plus the global cap (raised from 30
  to 60 for a few friends). Disabled users get the same generic error.
- Claims `{u, e, p}` checked against that user's row (cached a few seconds, like the epoch now):
  "log out everywhere" bumps only your epoch; changing your password changes only your fingerprint.
- Sign-up: the owner creates an invite and shares the link `/join#<code>` (the code sits in the
  URL fragment, so it never reaches server logs or a Referer). `POST /api/auth/signup` with code,
  username, password: single use, expiring, revocable, rate-limited per IP; a bad code and a taken
  username give errors that don't reveal which invites exist. Password: at least 12 characters and
  not on a short common-password list.
- Owner admin: list users (last active, hunts, eBay calls), disable/enable, delete, create/revoke
  invites. The owner can't be disabled or deleted.
- Delete my account: needs your password; removes every row of yours (cascade), your uploads and
  photo, and your push subscriptions. Shared listings stay.

## 5. Ranking at a few users

- Scores per user in `listing_scores (user_id, listing_id)`, only for **active** users (seen in
  the last 30 days); inactive users are rescored when they come back. Scoring stays incremental:
  each user has their own version/dirty state, new listings are scored for every active user in
  the same pass (embeddings are computed once, shared).
- Planner: every active user's queries are merged and deduplicated by (text, category), keeping
  the highest price cap; one rotating cursor, same batch size, same >= 10 s per request. More
  users = each search comes round less often, never more requests.
- Caps for friends (owner unlimited as now): 5 hunts, 60 min minimum interval; sold-price checks
  for up to 30 branded wardrobe items (Grailed load); LLM re-rank owner only (it costs you money).
  The owner's admin shows eBay calls per user per day.

## 7. Profile

Decisions (17 Nov): the avatar takes the cog's place; about 1-5 friends (caps below); friends see
the system font and lucide icons, only the owner's account loads Neue Montreal and Basil (the
font CSS and icon data are fetched only after an owner login); friends' alerts are Web Push only.

- **Web**: the cog becomes the avatar button (photo or initials). It opens a Profile sheet:
  photo (tap to change or remove), display name (editable), @username, member since, role badge
  for the owner; rows: Settings (today's settings page, unchanged), Sources, Change password, Log
  out, Log out everywhere, Privacy, Delete account; owner only: Friends and invites, eBay usage.
- **iOS**: the gear becomes the avatar button in the header's glass group. It opens a Profile
  sheet with native grouped rows; Settings pushes inside that sheet (today's settings pages,
  which are already a modal stack). Photo via expo-image-picker
  with the square crop, uploaded to the same endpoint.
- **Photos**: `PUT /api/me/avatar` (multipart, one image, 10 MB), through the existing upload
  sanitiser (EXIF stripped, re-encoded), centre-cropped to 512 px JPEG; `GET /api/me/avatar?v=`
  needs login (owner admin may see friends' photos). No photo = initials on a tinted circle.

## 8. Steps (each its own commit, your OK before each)

1. Users and login (backend): `users`, `invites`, owner seeded, username login, per-user epochs,
   sign-up, change password, admin endpoints, tests.
2. Per-user data and ranking: migration 0019 (dry-run on a copy of the real DB first), scoped
   queries everywhere, per-user scoring/planner/hunts/price drops/estimates with caps, IDOR suite.
3. Alerts per user: per-user Web Push for everyone, ntfy/Telegram for the owner, test alert and
   recent alerts per user.
4. Profile and photos (backend): `/api/me`, avatar upload/serve, delete account.
5. Web app: username login, `/join` sign-up, avatar button + Profile sheet, Settings inside it,
   Sources for everyone, owner admin, privacy note, friends' font/icons.
6. iOS app: username login + token migration, avatar button + Profile sheet with photo, inline
   titles on every tab (light/dark, Reduce Transparency).
7. Security pass with `docs/security-audit-prompt.md`; fix and test every finding.
8. Docs, release notes, tag `v2.1`; iOS build when you say.
